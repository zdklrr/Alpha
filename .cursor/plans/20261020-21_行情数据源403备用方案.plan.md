# 行情数据源 403 备用方案（东财 → 腾讯）

> 关联计划：`.cursor/plans/20261020-20_Windows本地部署Alpha选股项目.plan.md`（本次为其补充项，不覆盖原文件）

## 背景 / 目标

Windows 本地部署后，一键初始化（`POST /api/jobs/kline-cache/initialize?window_days=120`）全部标的失败：

```
[market_data_client] GET json failed: https://push2his.eastmoney.com/api/qt/stock/kline/get
(Client error '403 Forbidden' for url ...)
```

排查结论（2026-10-20，本机 127.0.0.1:10809 出口）：

| 目标 | 结果 |
| --- | --- |
| `push2his.eastmoney.com/api/qt/stock/kline/get` | 403（直连 + 走系统代理均是 403，加 Referer/UA 无效） |
| `push2.eastmoney.com/api/qt/ulist.np/get` | 403（东财 `/api/qt/*` 整段被拦） |
| `quote.eastmoney.com/sh600000.html` | 200（仅网页路径可用） |
| `ifzq.gtimg.cn/appstock/app/fqkline/get`（腾讯） | 200 ✅ |
| `web.ifzq.gtimg.cn/...` | 高频后返回 501 反爬 JS 挑战页 |
| `proxy.finance.qq.com/ifzqgtimg/appstock/app/newfqkline/get` | 200 ✅ |
| `finance.sina.com.cn/.../klc_td_sh.txt`（交易日历） | 200 ✅ |

目标：在不改动上游业务逻辑的前提下，让 K 线同步在东财不可用时自动切换到腾讯备用源，
并且单轮全市场同步（5000+ 标的）能在可接受时间内跑完。

## 验收标准

1. `POST /api/jobs/kline-cache/initialize?window_days=120` 返回 `status=running` 且 `total_symbols ≈ 5000`
2. 同步过程中 `success_symbols / synced_symbols ≥ 0.98`，`failed_symbols` 接近 0
3. `GET /api/jobs/kline-cache/progress` 的 `progress_pct` 能到 100
4. `GET /api/funnel` 返回非空漏斗（依赖 K 线缓存）
5. `app/services/market_data_client.py` 单元测试全通过

## 风险与回滚

- **风险 1：腾讯反爬**。高频访问会返回 501 JS 挑战页（已实测）。缓解：全局限速 0.2s/次、
  多域名轮换、单域名失败冷却 300s。若三域名全部被封，K 线同步会退化为「无数据」而不是报错。
- **风险 2：成交额为估算值**。腾讯接口不返回成交额，估算误差约 1%~2%，会影响依赖绝对成交额阈值的策略。
  数据落库时 `source=tencent`、`fallback_reason=eastmoney_unavailable`，可按来源区分与回溯。
- **风险 3：科创板成交量单位**。688/689 上游返回「股」，已按前缀折算为「手」；若上游口径变化需复核。
- **回滚**：`git revert` 本次提交即可恢复纯东财实现；本地数据表可 `DELETE FROM kline_daily` 后重新同步。

## 关键决策记录

1. **为什么保留东财为主源**：上游默认行为，东财在本机以外环境可用；只在连续失败后降级，不改变既有语义。
2. **为什么用腾讯而不是新浪**：新浪 `stock_zh_a_daily` 每次返回全量历史（单标的 ~6400 行），
   5000 标的代价过高；腾讯按窗口返回，payload 小且稳定。
3. **为什么加限速**：实测 ~8 req/s 触发 501 反爬；限速 5 req/s 全市场单轮约 17 分钟，可接受。
4. **为什么改 start.ps1**：Windows 上日志文件句柄释放有延迟，硬删除会让启动脚本整体失败，必须 best-effort。
